# The full vision — kernel plan-IR SDK, end to end

One picture spanning all three layers: **kernel Rust → C ABI → C++ SDK → DuckDB engine**. Companion
to `SDK_API_DESIGN.md` (the C++ API in detail) and `SDK_FFI_INVESTIGATION.md` (the Rust/ABI backing,
verified against source). Design only — nothing implemented.

---

## The one-sentence thesis

> The kernel describes *what* to read as an engine-neutral **plan IR**; the engine decides *how* to
> execute it. Everything else — SQL generation, DuckDB dialect, drive cadence, async — is the
> engine's business, not the kernel's.

This inverts today's boundary (`plan_to_sql.rs` puts DuckDB's SQL dialect *inside* the kernel). The
kernel becomes dialect-pure; DuckDB owns lowering.

## The spine: one drive loop, four concepts

Everything hangs off a single interaction pattern the whole stack shares:

```
build a StateMachine  →  drive it (engine runs each Reduce)  →  get an inert value
```

Twice: **snapshot SM → `Snapshot`**, then **`Snapshot`.scan_sm(kind) → scan SM → `Scan`**.

| Concept | Kernel Rust | C ABI | C++ SDK |
|---|---|---|---|
| **State machine** (drivable, reduce-bearing) | `CoroutineSM<R>` (impl of `trait StateMachine`) | `enum FfiSm` handle | `StateMachine<T>` (`next`/`submit`/`build`) |
| **Request** (what the kernel needs) | `EngineRequest::{Reduce{nodes,terminal,sink}, SchemaQuery}` | `delta_sm_next` + `_reduce_plan` + `_take_reducer` | `variant<Reduce{plan,reducer}, Done>` |
| **Reducer** (consumes reduce output) | `ReducerHandle` (`apply`→`KdfControl`, `finish`) | `delta_reducer_apply`/`_finish` | `Reducer` (`apply`/`finish`/`apply_all`) |
| **Value** (inert result) | `Snapshot` / `ResultPlan` | `SharedSnapshot` / `SharedScan` | `Snapshot` / `Scan` |
| **Engine** (runs a plan) | — (engine-side) | — | `Engine::execute_to_arrow(plan)->ArrowStream` |

`SchemaQuery` (footer reads) is resolved kernel-side inside `StateMachine<T>`, so the engine only ever
sees `Reduce | Done`.

## Layer-by-layer

### 1. Kernel core — untouched, already right

The SM framework is already generic (`trait StateMachine { type Result }`) with concrete per-terminal
implementations (`CoroutineSM<Snapshot>`, `CoroutineSM<ResultPlan>`). The kernel keeps describing
reads as an IR plan. **This layer does not change** (verified — FFI §6). The whole re-arch is about
*transport and lowering*, not kernel semantics.

### 2. Kernel FFI — enum-wrapped handles, proto transport

The FFI's job: expose the generic SMs through a C ABI, and ship the plan as proto bytes.

- **`enum FfiSm { Snapshot(StateMachine<Snapshot>), Scan(StateMachine<ResultPlan>) }`** — the type C
  loses at the ABI is recovered by a runtime tag, not `dyn` erasure. The arms *are*
  `StateMachine<Snapshot>` / `StateMachine<Scan>`; the enum just puts them behind one opaque handle.
  `unsafe impl Send` (single-owner-cursor contract) makes it a `#[handle_descriptor]` target despite
  genawaiter's `!Send` `rc` coroutines (FFI §6).
- **`next`/`submit` are `T`-agnostic** (2-arm forward); **`build_snapshot`/`build_scan`** are
  type-specific and assert the arm. No result-union — the C++ `StateMachine<T>` template keeps `T`.
- **Proto transport**: `result_plan_to_proto` (exists) for `Scan::plan`; `struct_type_to_proto`
  (exists) wrapped for `Snapshot::schema`; `from_ffi` (exists) for reduce Arrow batches. The C++
  proto structs are generated kernel-side by `build.rs` (`protoc --cpp_out`, done in Stage 0).
- **~15 exports, 4 new handle types** + reuse of mainline `SharedSnapshot`. Errors via `ExternResult`
  (idiomatic) or the current `out_err` string (decision §4). Proto-only — **no `_sql`**.

### 3. Kernel-shipped C++ SDK — the nice API

`delta_kernel_sdk.hpp`, header-only, C++17 (it returns parsed protos). Pure C++ out — no handles, no
`_free`, no `Kernel*` types, no SQL, and the engine's vocabulary never contains "reduce".

```cpp
SnapshotBuilder(path, version) → snapshot_sm() | snapshot(engine)
StateMachine<T>: next()->variant<Reduce,Done> · submit(EngineResult) · build()
Engine::execute_to_arrow(plan)->ArrowStream          // pure IR-plan → Arrow, reduce-agnostic
drive(StateMachine<T>, Engine&)->T                   // sync loop-hider
Snapshot: version() · schema() · scan_sm(kind,pred) | scan(engine,kind,pred)
Scan: plan()                                          // the plan the engine faithfully executes
Reducer: apply(batch)->Control · finish() · apply_all(stream)
```

The **passive** `StateMachine` (never blocks in `next`) is what makes it async-agnostic — sync vs.
BLOCKED/wake is entirely the caller's choice, the SM is identical either way.

### 4. DuckDB engine — owns the dialect, sync + async

Engine-side, mostly in the C++17 island:

- **`DuckDbEngine : delta::Engine`** — `execute_to_arrow(plan)` runs the IR plan in DuckDB, yields a
  pull `ArrowStream`. Dumb; knows nothing of reducers/SMs.
- **`DeltaPlanBuilder`** — `plan::Plan (proto) → duckdb::LogicalOperator`. The heart of Stage 2; the
  ~950 lines of dialect that *leave* the kernel land here.
- **`SchemaToDuckDB` / `ToKernelPredicate`** — the other dialect conversions.
- **`DeltaSnapshot`** — composes `delta::Snapshot`; `ScanOperator(kind,filters)->LogicalOperator`
  (sync) and `AsyncScan(...)->DuckDBAsyncDriver` (BLOCKED/wake).
- **`DuckDBAsyncDriver<T>`** — pumps the raw passive `StateMachine` against DuckDB's
  `InterruptState`/BLOCKED. Lives engine-side, never in the kernel. **No `DuckDBAsyncEngine`** — the
  `Engine` contract is synchronous by construction; async collapses "make Arrow" and "can we step"
  into one scheduler question, which is the driver's job. (DuckDB has no `future<T>`; its async is
  poll+waker, so the driver is a pump: `pump()->variant<Blocked,T>`.)

The **C++11/C++17 seam**: anything touching parsed protos (the SDK header, `DeltaPlanBuilder`,
`DeltaSnapshot`) is a C++17 island, because protobuf/Abseil force `cxx_std_17` and DuckDB pins C++11
(mixing aborts on `LogicalType::VARCHAR` ODR — Stage 0's lesson). The C++11 extension TUs reach the
island through a narrow non-proto façade.

## Two user journeys (the payoff)

**Sync (metadata / can-block):**
```cpp
DuckDbEngine engine{ctx};
Snapshot snap = SnapshotBuilder(path, v).snapshot(engine);
Scan     scan = snap.scan(engine, ScanKind::Data, pred);
LogicalOperator op = DeltaPlanBuilder(ctx).Lower(scan.plan());
```

**Async (DuckDB BLOCKED/wake):**
```cpp
state.driver = deltaSnapshot.AsyncScan(ScanKind::Data, filters);   // holds StateMachine<Scan>
// per GetData:
auto r = state.driver.pump(ctx, interrupt);
if (holds<Blocked>(r)) return SourceResultType::BLOCKED;
state.plan = DeltaPlanBuilder(ctx).Lower(std::get<Scan>(r).plan());
```

Same SM, same passive primitives; only the driving strategy differs.

## Why each cut is where it is (the design spine)

- **Kernel emits IR, not SQL** → kernel is dialect-pure; every engine writes its own lowering once.
- **Proto is the transport** → single source of truth for wire types (kernel generates both Rust and
  C++ structs); no encoder/decoder skew.
- **State machine is passive** → the async boundary; DuckDB drives, kernel never blocks/schedules.
- **Enum-wrapped handle, not `dyn`** → recover the FFI-lost type with a runtime tag; no vtable, no
  terminal-mapping, no result union.
- **`Engine` is sync + reduce-agnostic; async is an engine-side driver** → the one clean synchronous
  abstraction stays in the SDK; DuckDB's poll/BLOCKED specifics never leak into the kernel.
- **Values are inert; `_sm()`/`(engine)` pair** → reduces live only on state machines; you take the
  machine (async) or the driven value (sync), uniformly.
- **C++17 proto island + C++11 façade** → parsed-proto ergonomics without the ODR abort.

| 4 | cutover to IR/`LogicalOperator`; delete `plan_to_sql.rs` + `_sql` FFI | pending |

Throughout 1.5–3 the **old SQL driver stays green** (1643/1656); the new proto SDK is validated
standalone (a C++17 harness driving snapshot+scan through it), and only Stage 4 removes the SQL path.

## The single highest-risk unknown

**`unsafe impl Send for FfiSm`** (FFI §6) over genawaiter's `!Send` `rc` coroutines. The reasoning is
sound (single-owner-cursor contract, mirrored by handle.rs's own `NotSync` test) but it's the one
place the Handle infra doesn't drop in mechanically. **Spike this first** (does a
`#[handle_descriptor(mutable=true)]` over the `Send`-wrapped enum compile + pass a real drive?) before
committing to the full enum-handle ABI. Everything else is assembling pieces that already exist.
